# AtCoder コーパス

AtCoder の公式問題を使い、Phase 6-E-B までの DSL が表現できる入力形式と制約を継続的に検証します。Phase 6-E-C では ABC355-B と ABC300-A に U1（除外付き重複なし一括初期化）を適用し、Phase 6-E-D では ABC385-E の頂点ラベルと辺順をU1で抽選します。Phase 7-Bでは、[拡張計画](../docs/CORPUS_EXPANSION_PLAN.md)の第1バッチ10問を追加し、**旧10問＋新10問の20問**を登録しました。DSL本体は変更していません。生成器と制約チェッカーは回帰テストにも使えます。各問題の公式URLと入力形式・制約の要約は `problem.toml` に記録します。 [DSL 言語仕様](../docs/DSL_SPEC.md)

## ディレクトリ構成

```text
corpus/
├── README.md
└── atcoder/
    └── <contest>/
        └── <problem>/
            ├── problem.toml
            └── generator.gen  # supported で必須
scripts/
└── verify_corpus.py
```

## メタデータ

`problem.toml` が分類と生成範囲の正本です。

| キー | 型 | 内容 |
| --- | --- | --- |
| `contest`、`problem` | 文字列 | ディレクトリ名と一致する ID。例は `abc355` と `d`。 |
| `url` | 文字列 | 公式問題のURL。通常は `https://atcoder.jp/contests/<contest>/tasks/<contest>_<problem>`。下記の明示的な例外のみ別slugを許す。 |
| `task_id` | 文字列、省略可能 | 通常の既定値は `<contest>_<problem>`。ABC095-Cだけは `arc096_a` を必須指定する。 |
| `description` | 文字列 | 行構造と要素数の要約。 |
| `constraints` | 文字列の配列 | 公式入力制約の要約。 |
| `status` | 文字列 | 以下の対応状況のいずれか。 |
| `coverage` | 文字列 | 以下の生成範囲のいずれか。 |
| `limitations` | 文字列の配列 | 生成対象の限定、値域を狭めた理由、または対応を妨げている理由。 `restricted` と `none` では必須。 |
| `missing_features` | 文字列の配列 | 不足機能。 `format-only` と `unsupported` では 1 項目以上必要。 |

公式の共通問題であるABC095-CのURLは `https://atcoder.jp/contests/abc095/tasks/arc096_a` です。検証側の例外表と `task_id` が一致し、URL全体も完全一致する場合だけ受理します。任意のtask_idで既存問題のURL検証を回避することはできません。旧10問のtask_id省略は従来どおり受理します。

### `status` の基準

- `supported` は、現行 DSL で公式入力制約をすべて満たすケースを構成でき、専用チェッカーで検証できる問題です。
- `format-only` は、入力の行構造と要素数を表現できるものの、公式制約の充足を保証できる生成方法や検証手段が揃っていない問題です。
- `unsupported` は、公式入力の行構造や値の型を現行 DSL で表現できない問題です。

ストレステスト用の生成器として利用できるのは `supported` です。回帰検証の成功件数もこの分類のうち全 seed で検証を通過した問題を数えます。

### `coverage` の基準

- `representative` は、主要な入力構造と制約を幅広く生成できる場合です。
- `restricted` は、公式制約を満たしつつ、規模、並び順、木の形などを限定する場合です。全 seed で入力が固定の場合も、固定した内容と理由を記載します。
- `none` は、有効な生成器を用意できていない場合です。 `format-only` と `unsupported` に使用します。

## 検証方法

Python 3.11 以降と、Cargo を含む Rust ツールチェーンが必要です。リポジトリのルートで実行します。

```sh
python scripts/verify_corpus.py
```

スクリプトは標準ライブラリでメタデータを検証し、Cargo が報告した実行ファイルをすべての生成に使います。各 seed で 2 回生成し、標準出力をバイト単位で比較します。そのうえで、行構造と公式入力制約を問題別のチェッカーで確認します。

共通の seed は `0`、`1`、`42`、`100`、`7`、`19`、`23`、`49`、`127`、`255`、`1024`、`65535`、`2^63`、`2^64-1` です。ABC370-B は seed `29` と `217` で `N=1` と `N=100`、ABC482-G は seed `2` と `17` で `T=1` と `T=10` も検証します。ABC385-E は共通の seed `49` で 3 頂点の木が得られます。

ABC400-D は共通14 seed に加え、1×2、2×1、1×1000、1000×1、1000×1000 に寸法を固定し、各 seed `0` と `42` で2回ずつ生成します。実際の生成器の寸法宣言だけを書き換え、全セル・座標・行数・幅・文字集合・異なる両端が道であることと再現性を確認します。最大寸法は1,000,000文字セル、出力は1006トークンで約1 MB、生成側の実行量も約400万単位で上限内です。1×1 は異なる2マスを置けないため有効入力がありません。

ABC355-B は `(N,M)=(1,1),(1,100),(100,1),(100,100)` に固定し、各 seed `0,42` で再現性と公式制約を検証します。`N=M=100` では `N+M=200` となり、値域 `1..=200` を全て使い切ることも確認します。固定歩幅37の剰余列に一致しない並びが生成されることを検査します。

ABC300-A は `N=1` で `A=B=1` と `A=B=1000`、`N=300` で同じ両端の値と正解位置 `1,150,300` を組み合わせた8プロファイルを、各 seed `0,42` で検証します。実際の生成器のスカラー宣言だけを固定するため、`Distractors`・分岐・幅1のコピーを含む生成処理をそのまま確認できます。さらに `N=9,A=7,B=11` を固定し、正解位置は抽選のまま共通14 seed で、正解位置の変化、同じ正解位置での誤答集合の変化、旧循環連番以外の列を検査します。

ABC385-E は通常の14seedでは `N=3..128` を維持し、別に `N=3,64,300000` を各seed `0,42` で検証します。P・Parent・Orderと出力の本体はそのまま、N宣言だけを固定します。既存チェッカーで木を確認し、出力トークン数とバイト数を実測して、配列容量・生成整数数・実行量の式とDSL上限を照合します。最大ケースを通常の14seed全てに適用することはありません。

旧10問では198条件を各2回生成します。旧10問すべて `supported`。`representative` は ABC300-A、ABC320-A、ABC355-B、ABC370-B、ABC400-B、ABC400-D の6問で、ABC355-D、ABC385-E、ABC420-E、ABC482-G の4問は `restricted` です。ABC385-Eはラベル・辺順の制限を解消した一方、通常生成の規模制限が残るため分類を維持します。問題ごとに結果と異なる出力の件数（固定条件も含む）を表示します。失敗時は問題名と原因を表示し、生成または入力検証の失敗には seed を添えます。予期しない失敗が1件でもあれば終了コードは非ゼロです。

新規は通常140条件と固定境界158条件を試行します。うち296条件で有効入力・同seedのバイト一致を確認し、2条件はABC216-Dの `N=M=200000` で容量上限への衝突を確認する試験です。この2条件は成功生成・公式制約検証の成功数に含めません。生成失敗の診断と空stdoutが再現することを確認し、診断が違う場合や予期せず成功した場合には試験自体を失敗させます。旧198条件と合わせ、494条件で有効入力を検証し、別に2条件の既知の容量未達を記録します。

生成時間（CLIの解析から整形まで）と外部チェッカー時間（Input読込み・全制約・行数終端確認）を分けて測定し、通常seedと固定境界を別集計します。追加の資源監査・出力ハッシュ・比較処理の時間はチェッカー時間に含めません。結果を保存するには次を実行します。

```sh
python scripts/verify_corpus.py --report corpus/reports/phase7b.json
```

[Phase 7-B実測レポート](reports/phase7b.json)には条件別のseed、生成・再生成・チェック時間、ソース/出力SHA-256、DSL行数、容量と仕事量の上界、制限診断を保存しています。固定プロファイルは実際の生成器の宣言や範囲だけを固定し、本体と出力構造を検証します。通常の生成範囲を広げたこととは区別します。

ABC303-Eのチェッカーは、まず木であることを確認し、最終状態の葉に隣接する頂点を必須の星中心に選びます。そこから距離が3の倍数の頂点を中心候補とし、各中心の次数が2以上、各非中心の次数が2以下かつ中心にちょうど1個隣接することを確認します。これで頂点を星へ分割でき、残りの辺は異なる星の葉同士のマッチングになります。星を縮約したグラフは木なので、公式手続きの順に接続できる証明になります。生成器内部のStars/Level/Offset/P/Orderは読みません。6頂点までの全1440個のラベル付き木を、接続辺の全削除パターンを調べる別方式と照合し、分岐する接続木も受理するテストを含みます。

チェッカーの正常・異常例には、空集合と非包含集合族、解けない盤面、挿入なしの問い合わせ、空にできない筒、異長の巨大整数を含みます。通常生成の制限を公式制約へ混入させないためです。少数seedの成功は任意seedの証明とはせず、生成構造・範囲・単一初期化・資源の根拠は[拡張計画の実測追記](../docs/CORPUS_EXPANSION_PLAN.md#10-phase-7-b第1バッチの実装検証結果)に記録します。

コーパスの回帰テストは次のコマンドで実行します。ABC355-B と ABC300-A では上記の境界・多様性と、チェッカーが重複、正解の欠落、値域・行幅・行数の違反を拒否することを確認します。ABC385-EはP・Parent・Orderから実際の出力を再構成し、辺集合を保った辺順の変化を確認します。専用DSLで配列・生成整数数と生成側・出力側の実行量を上限まで埋め、超過時の拒否も検証します。ABC400-D は不正な寸法・行長・文字・座標・端点の一致・壁の端点、ABC420-E は辺の重複、不正な端点、種別と合わない行幅の拒否を検証します。種別1が種類2・3の間に現れる入力、辺追加や種類3がない入力、同一seedの再現性も確認します。

```sh
python -m unittest discover -s scripts -p 'test_*.py'
```

## U1を適用した生成範囲

| 問題 | 変更前 | Phase 6-E-C の生成方法と改善 |
| --- | --- | --- |
| [ABC355-B](atcoder/abc355/b/problem.toml) | 歩幅37の剰余列を開始位置だけ変え、A・Bに分割 | `A in unique(1..=200)` の後に `B in unique(1..=200) except(A)`。公式範囲のN,Mを保ち、値の組と各配列の並びを抽選する。固定したN,Mについて両配列を通した順序付き標本が一様になる構成。 |
| [ABC300-A](atcoder/abc300/a/problem.toml) | 正解位置を基準とした循環連番 | 正解位置を抽選し、`Distractors[N]` を `unique(1..=2000) except(A+B)` で生成。正解位置にはA+B、それ以外には対応する候補を1回ずつ初期化。N=1でも配列長は正。固定したN,A,Bについて正解位置・誤答集合・順序を抽選できる。 |
| [ABC385-E](atcoder/abc385/e/problem.toml) | 頂点1を根として親の番号が子より小さい木、子番号の昇順で辺を出力 | 親配列の構成は維持し、`P in unique(1..=N)` でラベルを置換。`Order in unique(1..=N-1)` の順に辺を参照し、出力側のifでu<vにする。通常のN上限128は維持する。 |

一様性は、U1の独立一様な乱数語を仮定する抽選モデルと生成構造に基づきます。ABC355-B は固定長での2回の抽選を結合した標本、ABC300-A はN個の相異なる候補から正解位置の1個を使わないN−1個の周辺分布と、一様な正解位置を組み合わせたものです。複数seedの観測は実装上の確認であり、一様性の証明として扱いません。N・M・A・Bを含む全有効入力の一様分布や、有限のseedで全列に到達することは保証しません。生成方法と境界検証により以前の構造制限を解消したため、2問を `representative` に更新しています。 [適用の根拠と確認結果](../docs/ADVANCED_GENERATION_CONSTRAINTS.md#11-phase-6-e-c-でのコーパス適用)

ABC385-Eは、内部の子i+1を親 `Parent[i]≤i` につなぐため、連結・閉路なし・辺の一意性を保ちます。PとOrderはそれぞれ全域の順列であり、置換・並べ替えと端点の昇順化でもその性質は変わりません。抽選モデルでは固定Nの任意の形・頂点ラベル・辺順を構成対象にできますが、親配列に由来する木の形の出現頻度には偏りが残ります。ラベル付き木や入力全体の一様性は保証しません。

### ABC385-Eの最大ケースの資源

P・Parent・Orderの3配列とNだけを保存し、子番号は添字から求めます。

| 対象 | Nについての式 | N=300000 |
| --- | --- | ---: |
| 配列セル総数 | `3N-2` | 899,998 |
| 生成整数数 | `3N-1` | 899,999 |
| 出力トークン数 | `2N-1` | 599,999 |
| 生成側の実行量 | `6N+3` | 1,800,003 |
| 出力側の実行量 | `3N-1` | 899,999 |
| 出力バイト数の上界 | `digits(N)+1+(N-1)*(2*digits(N)+2)` | 4,199,993 |
| U1の最大作業列ペイロード（操作ごと） | `8N` | 2,400,000バイト |

最大ケースの出力はseed 0で3,977,870バイト、42で3,977,189バイトでした。いずれも上界と8 MiB以内です。作業列ペイロードはプロセス全体のメモリ量とは区別します。 [構成の根拠・残る制限](../docs/ADVANCED_GENERATION_CONSTRAINTS.md#12-phase-6-e-d-での木のラベルと辺順)

## 問題の追加手順

1. 公式問題文の入力形式と制約を確認し、`atcoder/<contest>/<problem>/problem.toml` に要約と公式 URL を書きます。
2. DSL の生成順と値域から、すべての生成入力が公式制約を満たすと説明できる構成を探します。限定した範囲や構造は `limitations` に記録します。
3. `supported` にする場合は `generate` と `input` を持つ `generator.gen` を追加し、[`verify_corpus.py`](../scripts/verify_corpus.py) の `CHECKERS` に問題専用のチェッカーを登録します。それ以外の場合は、実装に必要な機能や検証上の不足をメタデータに記録します。
4. 検証スクリプトを実行し、問題の分類と結果を確認します。

## 制約チェッカーの方針

チェッカーは出力を行ごとに読み、要素数、整数の範囲、文字列の幅・文字集合、要素間の関係、行の過不足を確認します。各判定に使う上限は生成器の設定値と独立に、公式制約から取ります。たとえば ABC385-E では辺数と端点を確認し、辺の追加で閉路ができず全頂点が連結することを確認します。3 頂点以上の木には長さ 2 のパスがあるため、問題文の「ユ木」にできるという条件も満たします。ABC482-G では各グラフが単純グラフであることに加え、ケースをまたぐ辺数の総和と `sum(A)^3` の総和をそれぞれ確認します。

## 既知の制限

- 有限の seed を使う回帰検証です。すべての seed に対する制約充足は、生成器の構成と値域から説明します。
- ABC300-A は長さ0を避けるため誤答候補をN個生成し、正解位置の1個を使用しません。N=1でも内部抽選は行います。コピーは既存どおり幅1の整数範囲で初期化します。2問の全有効入力に対する一様性は保証しません。
- ABC385-Eの通常生成はN≤128で、最大30万頂点は境界用のDSLで個別に検証します。木の形・入力全体の一様性は保証しません。ABC482-Gは現行U1の配列全体対象だけではケースごとの独立な辺集合抽選を表しにくいため、生成器を変更していません。
- ASCIIの固定幅文字グリッドと、実行時に選ぶ単一文字列の長さは生成・検証できます。Unicode、配列内で行ごとに異なる長さの文字列の一般的な生成は対象外です。ABC420-Eの行幅の異なるクエリは整数の条件分岐で任意の順序に並べます。辺の形と規模には引き続き制限があります。
- 旧10問ではABC355-B、ABC300-A、ABC385-E、ABC400-Dの上記境界を検証します。新10問の達成・未達境界は第1バッチの表と実測レポートを参照してください。AtCoderの解答プログラムの正しさの評価は対象外です。
