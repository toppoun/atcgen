# Phase 8-A：資源上限と出力・保存方式の設計

調査日：2026-11-18。基準コミット：`77734c9894f10dd90a16520b695429f3bf566ccb`。

本書は調査・設計であり、実装済みの仕様ではない。DSL本体、文法・型、コーパス40問、テスト、依存関係、既存レポートは変更しない。以下の改善件数・計算値は、明示したPhase 7の実測を除き、ソースと制約から導いた設計上の予測である。新しい生成成功として集計しない。

推奨は、まず出力のトークン列・行末配列の保存をなくし、**計数検証→必要量を一度だけ確保→非公開の最終文字列へ整形→成功後にCLIへ返却**とすること。その後、出力を2,000,000トークン・16 MiB、生成整数数を2,000,000にする。整数配列は別の変更として個別・合計とも2,000,000セルを推奨する。文字セル、実行量、U1の上限は据え置く。配列上限の引上げで大規模疎グラフや解答出力量の保証まで解決するとは扱わない。

「エラー時stdoutは必ず0バイト」について、現行実装が提供している生成・検証エラーの原子性と、stdout自体のI/O障害を区別する必要がある。任意のstdoutへ書込みを開始した後のI/O障害まで含む絶対保証は、現行CLIにもなく、標準ライブラリによる可搬な実装では実現できない。この契約上の未解決点を第5・10節に明記する。

## 1. 現行の資源管理構造

### 1.1 調査資料と処理順序

正本は [DSL_SPEC.md](DSL_SPEC.md) 第3.2・5・8節、[CORPUS_EXPANSION_PLAN.md](CORPUS_EXPANSION_PLAN.md) 第12節、[ADVANCED_GENERATION_CONSTRAINTS.md](ADVANCED_GENERATION_CONSTRAINTS.md) 第9.3・12節、および [phase7d.json](../corpus/reports/phase7d.json)。過去の [phase7b.json](../corpus/reports/phase7b.json)・[phase7c.json](../corpus/reports/phase7c.json) も照合した。Phase 7-DのSHA-256は `8099383145c37af1268d5e3ed0d61faefe5950c29be2f73c3f3ab7d116768e0f`。

[src/lib.rs](../src/lib.rs) の公開APIは `generate(source, seed) -> Result<String, Error>`。処理順は以下である。

1. Parserがソースを借用してASTを構成する。
2. Validatorが全宣言・ループ名を登録し、型・スコープ・宣言順を検証して束縛済みプログラムを作る。
3. Generatorが宣言順に値を生成し、全値をケース終了まで保持する。
4. Outputが読み取り専用の値を使ってinputを実行し、検証済みトークンと行末を保存する。
5. Outputが検証済みトークンを最終Stringへ整形する。
6. CLIが成功したStringを受け取って初めてstdoutをロックし、`write_all`、`flush`を行う。

値の生成、出力検証、整形の順序を変えて乱数を再実行する設計は採らない。

### 1.2 判定箇所・確保順序・不足している保証

| 層 / 実装 | 現在の資源判定・順序 | メモリと失敗処理 |
| --- | --- | --- |

| GeneratorのU1 | 対象の未初期化検査→幅検査→除外列確保・左から読取り→sort/dedup/範囲外除去→候補数→作業容量・生成数・仕事量→候補列確保・昇順列挙→抽選→対象へ反映 | 作業列に `try_reserve_exact` を使い、失敗を行・列付きErrorへ変換する。全抽選前に必要な検査・確保を完了。各U1終了時に作業列は解放され、他のU1や出力Stringと同時保持しない |
| [Output](../src/output.rs) | inputの選択分岐・反復順で読取検証。配列全体は展開前に全長のトークン残量を検査。各値の十進長・区切り、各行末LFをバイト数へ加算 | `Vec<Token>` に整数値・文字・文字列slice、`Vec<u32>` に空行を含む行末オフセットを保存。pushは通常確保。検証完了後 `String::with_capacity(bytes)`。整形中は値・両Vec・Stringが共存する |
| [CLI](../src/main.rs) | 引数・seed→`fs::read_to_string`→公開API→stdout | 生成前の読込にもファイルサイズ上限はない。生成等のErrorはstderrへ出し終了1、stdout未書込み。stdoutのwrite/flushエラーは一部書込み後にも起こり得る |

Outputの文字列トークンはsliceを借用するが、整数は各再出力につきTokenへ複写する。最終Stringは文字列内容も複写する。空行はトークンを消費せず行末Vecを増やすため、**行数はトークン数以下とは限らない**。1行1LFなので行数は出力バイト数以下である。

### 1.3 独立に維持する上限

| 資源 | 現在 | 独立に必要な理由 |
| --- | ---: | --- |
| 出力トークン | 1,000,000 | 同じ値の大量再利用を制限。生成数・保存セル数からは導けない |
| 出力バイト | 8,388,608 | 文字列長、整数の桁数、負号、空白、LFを制限。少数トークンでも超過する |
| 生成整数 | 1,000,000 | 非出力のスカラー・中間値・整数初期化も制限。未初期化配列容量や文字セルと異なる |
| 整数配列セル | 個別・合計各1,000,000 | 未初期化領域も確保するため、生成整数数とは別の保存予算 |
| 文字セル | 寸法・積・合計各1,000,000 | ASCIIの保存容量。再出力回数や文字生成処理回数とは別 |
| generate/input累積実行量 | 各10,000,000 | ほぼ出力しないネスト、条件、U1内部走査を制限。両ブロックは別予算 |
| 1回のforの反復数 | 1,000,000 | 空本体にも適用。累積実行量の適用されない従来形式も保護 |
| U1の幅 / 除外読取数 | 各1,000,000 | 疎な結果でも全候補走査・除外読取に費用がかかる。通常整数の値域とは別 |
| U1作業列ペイロード | 16,000,000バイト | `8*(W+e)`。対象配列、出力、アロケータ等を含むRSS上限ではない |

累積実行量は全ソースへ一律に適用されない。ネストしたfor、if、rowを構文として含むブロック、およびU1のあるgenerateで有効になる。単層forの行出力だけの従来形式では無効のまま。文1単位にforの反復数を事前加算し、U1は `1+k+W+e*ceil(log2(e+1))`。この適用条件と課金順序を今回の上限改定に便乗して変更しない。仕事量は式の文字数・平坦な演算子数やCPU命令数の厳密な上限ではない。

### 1.4 算術オーバーフロー対策

- 整数式はi64のchecked add/sub/mul/div/rem/neg。ゼロ除算と `i64::MIN / -1` 等を拒否する。
- 範囲幅は端点をi128へ広げてから差と包含端の1を加える。i64全域の幅 `2^64` も表現できる。forの幅検査後にi64/usizeへ変換し、反復値の最終加算は検証済み範囲内にある。
- 宣言長・添字は正数または1始まり範囲を検査してからusizeとして使用する。文字列の積はchecked、行×幅のオフセットは検査済み全セル数以下という不変条件に依存する。
- 容量・生成数・出力数・バイト数は「増分 > 上限−使用済み」を比較してから加算する。U1のpayloadはchecked add/mul、仕事量式はu128で計算してusizeへ検査変換する。除外容量見積りのsaturating加算は読取り上限までに留める目的であり、実際の読取り超過を許容しない。
- 整数の出力桁数は `unsigned_abs` によりi64最小値も安全に計数する。Token数のu32変換は現在の固定上限に依存する。
- SplitMix64のwrapping add/mul、棄却閾値のwrappingは定義された乱数演算である。資源カウンターにこの方式を転用しない。

### 3.2 案Cの方式別比較

| 方式 | メモリ・時間 | 原子性・互換性・採否 |
| --- | --- | --- |
| 現在のToken列をfallibleに逐次拡張 | 1回のinput評価＋整形。Token/行末/最終Stringが併存。再確保時に旧・新領域が共存し得る | 小さい改修だが、空行の行末保存も残る。移行用の選択肢 |
| 非公開Stringへ1回の走査で追記 | 最終内容のみ保存。倍増方式では最終容量に余りがあり、再確保時に旧＋新の一時ピーク。上限16 MiBを一括確保すると小入力にも過大 | 全エラーまでstdoutへ渡さなければ生成原子性は守れる。次点。検証と整形の交錯で診断順序を変えない注意が必要 |
| **計数検証後、正確な必要量を一度確保し再走査** | 最終Stringのみ。2回の決定的input評価。再確保不要の設計にできる | **第一推奨**。最初の走査は現行の検査順を保持。生成値は不変、乱数再実行なし。既存の全検証後整形という契約に近い |
| 全DSLの静的な最悪出力量のみで予約 | 選択されない巨大分岐まで計上すると実際は安全な入力も拒否し、過大予約になる | 採らない。実際に選択したinputを事前検証する |
| 一時ファイルへ非公開スプールし、完成後stdoutへコピー | RAMはチャンク程度、ディスクはB、書込み＋読込み＋stdoutでI/O増。公開String APIでは結局メモリへ戻す必要あり | 検証・書込・flush・seekは公開前に検査できるが、コピー途中の一時ファイル読取失敗は部分stdoutを残す。厳格な要件を満たす標準方式として採らない |
| 一時ファイルを全文読戻し後にstdoutへ渡す | 一時ファイル＋最終String、読戻しピークB。Token列は不要だが推奨方式よりI/Oが多い | 読戻し失敗までstdout 0は守れる。今回の16 MiBでは利点が小さい |

一時ファイル案を将来検討する場合も、外部依存なしの `temp_dir`、`OpenOptions::create_new` による排他的作成、衝突時の有界リトライ、ファイルサイズ上限、flush/seek検査、ハンドルを閉じてから削除するRAIIが必要。名前生成にDSLのPRNGを使わない。Windowsでは開いたままの削除・置換を前提にできず、UNIXのunlink済みファイルだけに依存する方式も採らない。パスだけを信頼した再openや固定名は避ける。異常終了時の残骸・保存領域不足・パーミッションも追加課題になるため、今回の第一実装に含めない。

## 4. 保存容量の改善案

### 4.1 比較の前提

現行DSLは整数の上書き・変数の再代入・配列の解放を持たない。宣言容量は全て累積する。inputは値の参照だけで、`i` や `Offset[t+1]-Offset[t]` を直接出力できない。したがって「補助配列を消して出力時に計算」「使用後に領域を再利用」とだけ書いても、現在のDSL内の実現案にはならない。以下はこの制約を満たす別ソースの候補である。既存ソースの幅1生成を処理系が勝手に削除する最適化は提案しない。

Wの数値は現在の実行規則に基づく値または保守的上界。新しい構成の上界は最終DSLの分岐配置で確定させる必要があり、本書では未実装である。構成の変更は同seedでも出力や乱数消費を変え得るため、旧ソースを保持した追加プロファイルで比較する。

### 4.2 ABC216-D：N=M=200000

[生成器](../corpus/atcoder/abc216/d/generator.gen) はMaxM[1]、Order[2N]、Color[N]、K[M]、Offset[M+1]。Colorは恒等表だがinputで整数式を出せないため必要であり、単純に削除はできない。Orderは2N個の個体をU1で並べ、Colorへの剰余添字で各色2回を保証する。

- A=`3N+2M+2`＝**1,000,002**。宣言時にOffsetで超過する。
- 全セル初期化＋N/MのG=`3N+2M+4`＝**1,000,004**。配列だけを緩和すると次はこれに衝突する。
- Wg=`13+6N+4M`＝2,000,013、Wi=`2+4M+4N`＝1,600,002。U1幅400000、作業列3,200,000バイトで各上限内。
- T=`2+M+2N`＝600002。Bは既存の保守式で≤4,200,014。全案で同じN/M、長さ・色の行形式を維持する。

| 案 | A / G（最大条件） | 仕事量・出力 | 多様性と達成範囲 |
| --- | --- | --- | --- |
| 1. 不要な境界補助を削減 | 最大固定プロファイルではMaxM[1]を削除し、Mを直接固定。A=1,000,001、G=1,000,003 | 現行以下、T/Bは上記 | 1セル削減だけでは不足。通常のM≤min(2N,200000)を保つ一般化は別に必要 |
| 2. 保存中間値を減らす | さらにOffsetを終端End[M]へ変更。最初の区画だけ別分岐、以後はEnd[t−1]+1から走査。Kは行の長さ出力用に残す。A=1,000,000、G=1,000,002 | 追加分岐込みでもWg/Wi各3,000,100以下を設計目安とする。T/B同じ | 区画と個体順列の構成範囲を保てるが、**現行G上限では未達**。G緩和と組み合わせる。End方式の実装時に正確な課金を検証 |
| 3. 生成構造を変更 | Order[2N]とColor[N]をP[N]の順列1本に置換し、`P[(j−1)%N+1]`を参照して2回繰返す。その他は現行のまま。A=`N+2M+2`=600002、G=600004 | Wg=`11+2N+4M`=1,200,011、Wiは現行と同じ。T/B同じ | 現行上限内。ただし球列は同じ順列の2連続に限定され、任意の2重多重集合の並びから大きく狭まる。最大規模達成を一般構造の改善と扱わない |
| 4. 配列上限を引上げ | A上限2,000,000だけではGで失敗。Gも2,000,000なら現行方式のA/Gを収容 | W/T/B/U1は全て内側 | 元の区画分割と個体順列を保つ。通常N≤4096等の運用範囲を変えるかは別評価 |

公式では正の区画長の総和2Nと各色2回が必要で、解がYesになることは入力条件ではない。[ABC216-D公式制約](https://atcoder.jp/contests/abc216/tasks/abc216_d)。

### 4.3 ABC251-F：N=633/M=200000と大規模疎グラフ

[生成器](../corpus/atcoder/abc251/f/generator.gen) は全候補 `C=N(N−1)/2` を列挙し、Parent[N−1]、U/V/Keep/Order各C、Prefix[C+1]、Label[N]を保持する。A=`5C+2N`、G=`5C+2N+3`。採用されない辺にもU/V/Keep/Prefix/Orderの容量と初期化が必要になる。

N=633ではC=200028、A=**1,001,406**、G=**1,001,409**。既存プロファイルは親を1、先頭200000候補を採用するよう固定してMを200000にしている。T=400002、B≤1,600,011、Wg≤2,405,420、Wi≤600058。配列だけを2,000,000にしてもGが残るが、A/G両方ならこの既存境界は可能になる。

| 案 | A / G | 仕事量・出力 | 多様性・限界 |
| --- | --- | --- | --- |
| 1. 既知Mに不要なPrefixを削除 | 固定N=633/M=200000ではMを既知値とし、Prefix[C+1]を省く。A=`4C+2N−1`=801377、G=801380 | Wgは上記上界以下、Wi/T/Bは同じ | 既存の固定辺集合＋Label/Orderの変動を保持できる。一般のランダムKeepからMを求める通常生成へそのまま適用はできない |

| 3. 疎な構造へ変更 | M=N−1の木ならParent/Label/OrderだけでA=`3N−2`、N/Mの2スカラー込みG=`3N`。N=200000で599998 / 600000 | Wg=`6N+4`=1,200,004、Wi=400000、T=400000、B≤2,800,000、U1幅≤200000 | 最大頂点の木は現在のDSL内で可能。木の形・ラベル・辺順を変えられるが、M>N−1の一般グラフを含まない。パス＋固定追加辺も別の狭い境界用構成 |
| 4. 配列上限を引上げ | A/G各2,000,000でN633の境界は可能 | 全候補方式のWはC比例、T/BはM比例 | N=200000の疎グラフには不足。上限だけで解決しない |

N=200000ではC=**19,999,900,000**、A=99,999,900,000セル。通常の64-bit表現なら整数セルだけで約1.6 TBの要求になる。個別配列長、合計配列、G、U1幅1,000,000、累積仕事量の全てが障害である。候補全域を1回のforで走査する部分も反復数上限を超える。Aだけを桁違いに増やす案は棄却する。

### 4.4 ABC298-C：Q=200000

[生成器](../corpus/atcoder/abc298/c/generator.gen) はKind/Card/Box/InsertPos/Choice各Q、Count[Q+1]。A=`6Q+1`＝**1,200,001**。挿入I回、問合せR回、I+R=Q（先頭は挿入）なら、実際のGは `3+5I+4R = 4Q+I+3`。レポートの `6Q+3` は保守上界で、全挿入時の実数 **1,000,003** と区別する。

現在のofficial-Q境界はN=1、カード/箱1、全挿入であり、解答整数数0の有効入力。T=600002、B=1,200,009。一般の行形式ではT=`2+3I+2R`、B≤3,200,014、Wg≤4,000,020、Wi≤800003、U1なし。

| 案 | A / G | 仕事量・出力 | 多様性・限界 |
| --- | --- | --- | --- |
| 1. Choice専用配列を省く | 種別2では未使用Card[i]、種別3では未使用Box[i]に選択番号を保存し、それをInsertPosの添字に使う。A=`5Q+1`=1,000,001、Gは元と同じ | 元と同程度、T/Bは同じ | 過去の任意挿入から選ぶ能力を保持。1セルの超過が残る |
| 2. さらに初期Countセルを省く | Count[Q]を「処理後の挿入数」とし、初回を別扱いにする。A=`5Q`=1,000,000、G=`4Q+I+2`、全挿入では1,000,002 | 追加分岐を含めWg≤5,000,100、Wi≤800003を目安とする。T/B同じ | 過去参照の構成範囲は保てるが、全挿入ではG上限変更も必要。解答出力量の問題は独立して残る |
| 3a. 全挿入の専用構造 | Count/InsertPos/Choiceと不要分岐を削除。Kind/Card/BoxでA=600000、G=600002 | Wg=800006、Wi=400003。T=600002、B≤3,200,014 | 公式Q最大を現行上限内で達成できるが、問合せを一切含まない。通常生成の置換には不十分 |
| 3b. 先頭1回挿入後、種別2/3のみ | Kind/Card/BoxでA=600000、G=400003。以後は最初のCard/Boxを参照 | Wg≤1,600,100、Wi≤800003、T=400003、B≤1,800,021。解答整数Q−1=199999 | 現行上限内で問合せを含む最大Q。ただし全問合せが同じ1枚・1箱に集中し、多様性は極めて狭い |

**問題側の解答整数総数≤200000は、atcgenが生成する入力Tとは別である。** 現行方式の「既存挿入を1件選んで問合せる」処理は空参照を防ぐが、種別2が返す重複カード数、種別3が返す異なる箱数の総量を制御しない。Q≤256ならI×R≤16384という保守的保証で十分だった。Q=200000ではI=R=100000ならI×R=10^10に達し得る。配列上限だけを広げて通常Q範囲を拡張してはならない。

多様な大規模列には、箱内の多重度・カードの箱集合と、残り解答整数予算を追跡する生成アルゴリズム、またはI×R等の構成上界で保証する明示的な制限が必要。例えばI×R≤200000の二段階列は安全だが、挿入と問合せの任意混在を失う。境界全挿入の成功とこの課題を別件にする。[ABC298-C公式制約](https://atcoder.jp/contests/abc298/tasks/abc298_c)。

## 5. 安全性・原子性・再現性の保証

### 5.1 推奨する出力処理

第一走査は、今のOutputの評価・検証順を維持したまま、T、B、現在行のトークン有無だけを保存する。Tokenの配列と行末配列は保存しない。配列全体の展開前チェック、参照の初期化検査、左からの評価、行末LFでの超過、選択した分岐だけの検査を維持する。

第一走査成功後、空のStringに対してBの `try_reserve_exact` を1回行う。確保できなければ整形開始前に明確な確保エラーを返す。B=0も扱う。第二走査は同じ束縛済みinputと不変のvaluesから同じ行を整形する。出力先は公開しない。整数は最大20バイトの固定スタック領域で十進化し、通常のString成長を伴う一時文字列を作らない。ASCII文字・文字列は同じ内容を追記する。

第二走査でもcheckedな長さ・残容量確認を持ち、予測を超えた場合は内部不整合としてStringを破棄する。`debug_assert`だけに安全性を依存しない。最終長B・トークン数Tの一致を確認してからStringの所有権を返す。最終出力のclone、VecからStringへのコピー、再度の容量変更は行わない。

論理的なinput仕事量は第一走査の1回分である。第二走査は新しい同条件の予算状態で同じ経路をたどるか、検証済み走査として扱い、1回目の課金残量へ重ねて加算しない。CPUの処理が2回になることは性能項目へ計上する。generateやPRNGを再実行して二度目の出力を作ることは禁止する。

### 5.2 確保前検査と確保失敗

通常整数配列・文字列・valuesの大きい確保にも、上限と `count*size_of::<T>()` のchecked検査、`isize::MAX`を超えない確認、`try_reserve_exact`→予約済み領域内の初期化を適用する。valuesは巨大なslot_countを無条件に一括予約せず、検査済みの宣言に合わせた有界のfallible確保へ改める。これを配列上限引上げの前提にする。上限内でも環境のメモリ不足なら「どの領域・要求数/バイト・位置で確保できないか」を区別して返す。U1の既存の対象変更前・抽選前検査を維持する。

制御用Vecは深さ32が分かっているので事前のfallible予約または固定長領域を使える。エラー表示用にも少なくとも静的メッセージへ退避できる設計を検討する。巨大な `format!` や診断文字列の無制限な複写を避ける。

ただし現在のParser/ValidatorのBox・Vec・HashMap、CLIのソース読込み、Error文字列は全てがfallibleではない。Rustの通常の確保失敗・OSの強制終了まで捕まえて必ずErrorを返せるとは記載しない。大きいランタイム領域の回復可能な確保失敗を明確化する改修と、任意ソースに対する処理系全体のメモリ保証は区別する。後者にはソース/総ノード/宣言数予算、静的構造の確保方式、割当失敗時の診断方法の追加設計が必要である。

### 5.3 stdoutの原子性の範囲

構文・型・生成・input検証・上限・整形・公開前の確保に失敗した場合、stdoutへ一切触れない。現在の遅い出力エラーのテストを維持する。行ごと・チャンクごとに検証しながらstdoutへ流す方式は採用しない。複数ケースのStressでも、不完全なケースを解答プログラムへ渡さない。

一方、現行の `write_all` は単一の原子的書込みではなく、途中まで成功してから失敗できる。flush失敗も同様である。`write_all`がwriteを繰り返すことは [Rust標準ライブラリのWrite契約](https://doc.rust-lang.org/std/io/trait.Write.html#method.write_all) でも確認できる。stdoutが端末、pipe、任意のリダイレクト先である以上、出したバイトをWindows/macOS/Linux共通で取り消す機能はない。16 MiBをpipeの原子的書込みに頼る案も成立しない。メモリバッファを完成させてもこの事実は変わらない。

したがって、要求を文字どおり**全I/O障害も含めてstdout 0**と解釈するなら、本書のどの方式も完了条件を満たさない。この点は実装前の契約確定事項であり、「エラー」と呼ぶ範囲を黙って狭めて達成済みとしない。推奨する実装範囲は、現行以上の生成原子性を持ち、公開後に新たな読取り・整形・確保の失敗経路を追加しないことである。

ファイル宛の保存なら同じディレクトリに一時ファイルを完成させてから置換する別契約を検討できるが、これはstdoutの解決ではなく、既存CLIにない出力先機能である。今回の実装案の前提にはしない。

### 5.4 再現性と互換性

SplitMix64、棄却抽選、整数/文字の幅1抽選、U1の昇順候補・前向き部分Fisher–Yates・最後の幅1抽選、未選択分岐の非実行を変更しない。出力の計数・再走査・メモリ確保・一時名生成はDSL乱数を消費しない。エラー検出順序も上限値の変更で到達可能になった後続エラー以外は原則維持する。

処理系が定数生成や未使用値を省く最適化、配列の自動解放、乱数列を再生する再生成、U1を別抽選法へ自動切替する変更は今回に含めない。第4節の省容量DSLは新しいソースとして評価し、旧ソースへのバイト一致とは別の実験にする。

## 6. メモリ・実行時間の見積もり

### 6.1 出力バイトとプロセスメモリを分離する

64-bit環境の典型的レイアウトでは、`Option<i64>`は16バイト、Tokenは24バイト、row_endは4バイト、Valueは40バイト程度。これらはRustの全ターゲット共通のABI保証ではないので、実装時は対象ビルドの `size_of` で記録する。以下はペイロードの設計見積りでありRSS実測ではない。

現在の整形ピークは概ね次式となる。lenではなくcapacityで評価する。

`16*A_capacity + C_capacity + 24*T_capacity + 4*R_capacity + B_capacity + P`

Pはソース、AST/束縛構造、Value管理、スカラー、スタック等である。U1中の作業列は別の生成ピークに加算する。通常のVecの成長係数やアロケータによる丸めは仕様上の固定値ではない。再確保時には旧領域と新領域が一時共存する場合もある。

例えば倍増に近い実装でT上限2,000,000のToken capacityが2,097,152なら約48 MiB。16 MiB分の空行だけでもrow_endは64 MiBになり得る。独立上限を単純合算した保守例では、整数配列2,000,000の約30.52 MiB、文字約0.95 MiB、最終出力16 MiBと合わせて約159.5 MiB＋Pとなり、再確保の一時領域はさらに別である。この独立合算は同時に各最大値を取る入力の存在を主張せず、厳密なRSS上限とも呼ばない。

推奨する計数＋1回確保ならT/Rの保存は不要となり、ランタイムの主な要求ペイロードは次の二つの大きい方になる。

- 生成ピーク：`16*A + C + U + P`。U≤16,000,000。
- 整形ピーク：`16*A + C + B + P`。B≤16,777,216。U1作業列は既に解放済み。

| 段階 | 配列 / 文字 / 出力 / U1上限 | 主な要求ペイロードの保守上界（＋P） |
| --- | --- | ---: |
| 出力方式を変更、全上限は現状 | A=1,000,000、C=1,000,000、B=8,388,608、U=16,000,000 | max(33,000,000, 25,388,608)＝33,000,000バイト、約31.47 MiB |
| 出力16 MiB、G=2,000,000、Aは現状 | 同上、B=16,777,216 | 33,777,216バイト、約32.21 MiB |
| 保存上限も推奨値へ | A=2,000,000、C=1,000,000、B=16,777,216、U=16,000,000 | max(49,000,000, 49,777,216)＝49,777,216バイト、約47.47 MiB |

Gは配列以外のスカラー数も制限するが、上記Aにはスカラーを含めない。Value/宣言メタデータはPとして別途数える。例えばスカラー2,000,000個だけでも、典型的なValue表現で約80,000,000バイトを別に要し、約47.47 MiBという表の範囲に含まれない。Stringの正確な予約はアロケータの実割当丸めやページ使用量を束縛しない。Vecについても [try_reserve_exactの公式説明](https://doc.rust-lang.org/std/vec/struct.Vec.html#method.try_reserve_exact) は過剰容量があり得ることを明記している。「要求ペイロードが約47.47 MiB」から「RSS≤48 MiB」と結論しない。ソース/ノード数が無制限の現在の処理系では、Pを定数化した全プロセスの有限上界は提示できない。

逐次拡張Stringの場合は旧＋新capacityのピークも加わる。最大16 MiB近くで8→16 MiBへ再確保すると、出力部分だけで約24 MiBが一時的に必要になり得る。現在のToken列とStringを両方残す段階的移行でも、片方を解放できる時点を実測する必要がある。最後に出力全体をcloneする案は採らない。

### 6.2 時間と測定計画

Phase 7-DはmacOS arm64・debugビルド・CLI timeout 30秒の観測で、プロセス起動とstdout取得を生成時間に含む。正常条件の最大観測はABC413-Eの約1.98秒。最大観測出力はABC241-Dの4,800,007バイト、最大観測TはABC253-Fの666670。ABC420-Cの通常最大境界は4,200,014バイト、生成約187 ms以下。未達のABC383-Eは約344–345 ms、ABC420-Cは約569–572 msのprobeであり、完成出力の生成時間ではない。

第一走査はinputの評価・読取・桁数計算、第二走査は同じ評価と整形を行う。生成は変わらず、概算は `生成時間 + 2*input走査時間 + 十進整形 + Bの書込み`。現在も検証・Token保存・整形があるため、総時間が必ず2倍になるとは推定しない。反対に、複雑な条件や長い式がある入力では評価の再走査が重くなる。時間上界を10,000,000単位から秒へ直接換算しない。

実装後は旧正常1,010条件、必須5境界、全空行・繰返し長文字列・i64最小値・U1最大作業列を含む入力で、生成、検証、整形、stdout書込、ピーク要求容量、ピークRSSを別に記録する。Windows/macOS/Linuxでrelease測定を行い、debug値と混ぜない。RSSはOSごとの単位・子プロセスの扱いを明記し、各ケースを新規プロセスで測る。測定のためのツールは開発用とし、実行時依存を追加しない。

Stressでは同時ケース数pならケースのピークは概ねp倍になる。ケース毎のT/B/A/G上限とは別に、同時実行数・キュー内の完成出力数・総一時保存量・時間切れを管理する。Stringを返す境界を維持し、完成ケースを処理後すぐ解放すれば統合しやすい。先に無制限スプールや無制限並列を導入しない。

## 7. 既存テストへの影響

### 7.1 成功と失敗を別々に比較する基準

実装前にPhase 7-Dの**全1,026条件**について、実際の展開済みソース・seed・生出力/終了コード/診断・ソースと出力ハッシュを新しい永続スナップショットへ保存する。既存 `/tmp/atcgen-phase7d-pokee3lp` は既存30問の772条件・正常764条件の保存であり、全1,010成功の基準の代替にはならない。消え得る一時パスだけに依存しない。

比較キーは問題ID、プロファイル、ソースSHA-256、seed。新プロファイルや省容量の別ソースは別キーとする。診断比較で除くのは一時ファイル名だけで、終了コード、行、列、エラー内容、stdout 0は保持する。

| 改善前→変更後 | 判定と記録 |
| --- | --- |
| 成功→成功、バイト一致 | `unchanged_success`。原則1,010件全てに要求。ハッシュだけでなく保存済み生バイトとも比較 |
| 成功→成功、バイト不一致 | `compatibility_violation`。制約検査が通っても違反 |
| 成功→失敗 | `compatibility_violation`。新予算導入などで変わる場合も黙認しない |
| 既知失敗→同じ失敗 | `unchanged_limit`。stdout 0、診断一致を検査 |
| 既知失敗→後続の資源上限で失敗、または同種の上限値だけ変更 | `changed_limit`。成功として数えない。Aだけ緩和してGに達した場合や、同じ配列長エラーの表示値が100万から200万へ変わる場合などを、位置・旧新内容付きの許容リストへ列挙 |
| 既知失敗→成功 | `newly_supported_limit_case`。期待リストと照合し、公式制約・資源・同seed再実行を新たに検証。従来バイト一致の分母へ遡及追加しない |
| 新条件・新ソース→成功 | `new_case`。旧ソース互換性の代替にしない |

最初の方式変更のみなら正常1,010・既知失敗16を全て維持する想定。出力上限改定後は既知出力失敗6が成功し、既知保存失敗10は残る想定。A/G各2,000,000まで対応すると、保存失敗のうちABC216-D 2、ABC251-FのN633 2、ABC298-Cの全挿入2、ABC401-F 2の**8条件**が追加成功し、ABC251-FのN200000-tree **2条件**が残る想定である。後者の旧ソースは全候補方式なので、別の省容量木が生成できても旧条件の成功へ付替えない。

この予測では既存1,026条件の内訳は最終的に正常1,024・残り未達2となるが、実装・検証前の見込みである。ABC355-D/ABC420-Eの新しい最大境界はこの分母の外に追加する。unsupported 1問は据え置く。

### 7.2 既存の比較器・資源テストの扱い

[compare_corpus_baseline.py](../scripts/compare_corpus_baseline.py) は「既知失敗が成功したらエラー」にする厳格な旧比較器であり、そのままでは許容する上限改善を検出違反にしてしまう。保護対象にはDSL本体・過去レポート等も入る。新しい比較器/明示的モードで上記遷移を分離し、旧比較器と旧記録を残す。資源変更を許す対象ファイルと、絶対に書換えない歴史資料を分け、広い除外設定で保護検査を無効にしない。

現行Rust97テスト、Python83テストのうち、`src/tests.rs`、`src/string_tests.rs`、`src/unique_tests.rs`、`tests/cli.rs`、Pythonのexpected_errorプロファイルには100万/8 MiBを前提とする期待がある。将来の改定では、新上限ちょうど/＋1の検査へ更新する一方、旧上限ちょうど/＋1が成功へ移るテストも残す。特に文字列9回出力のCLIテストは、新16 MiBでは失敗しなくなるので値を単純放置しない。今回はテストを変更・追加しない。

将来実装で必要な検証は次のとおり。

- T/B/G/A/文字/仕事量をそれぞれ他の上限に当てず、上限一致と1超過を検査する。全配列参照と再利用、スカラー、文字列・文字列配列を含める。
- B上限ではLFと区切りが最後の1バイトになる条件、T=0の大量空行、rowの空行を検査する。行数≤Tという誤った仮定を防ぐ。
- 遅い未初期化、添字、条件式、算術、第二走査の内部不整合、公開前予約失敗を失敗注入で検査し、stdout 0を要求する。実メモリを枯渇させるテストは使わない。
- i64両端、usize変換不能、寸法積、仕事量の広い型からの変換、32-bitを想定した容量計算を検査する。64-bit OSだけの成功をusize安全性の証拠としない。
- 既存の独立PRNG/U1 golden値と、全1,010件の成功バイト一致を保つ。再走査の有無で抽選器呼出し数が変わらないことを確認する。
- 必須5出力境界と、第4節の4問を、出力だけ緩和・Gも緩和・Aも緩和の別段階で確認する。ABC298-Cは入力Tと解答整数総数を両方検査する。

新レポートは例として `phase8b-output-buffer.json`、`phase8b-output-limits.json`、`phase8c-storage-limits.json`、`phase8c-low-storage.json` に保存する。`phase7b.json`、`phase7c.json`、`phase7d.json` はハッシュで保護し、ツールの出力先指定でも上書きを拒否する。既存の一部スクリプトは7B/7Cだけを保護する箇所があるため、7Dも含む新しい保護を実装する。

| 資源 | 推奨値 | 導入段階・根拠 |

2,000,000は各資源で独立に判定し、一つを満たせば他を免除する契約にしない。例えば配列長2,000,000が宣言できてもU1幅は1,000,000のままで、全長のU1初期化はできない。生成整数2,000,000でも同数の配列セルと別のスカラーを全て初期化できるわけではない。20桁整数2,000,000個の出力は16 MiBを超えるので、Tの上限内でもBで失敗してよい。

最小値を各衝突の直上にする案より余裕を取るが、AtCoder全問題・将来の全大規模入力を収容する値とは主張しない。上限はハードウェアやseedで自動変更せず、バージョン化された決定的な契約にする。ユーザーが無制限へ解除するCLIは今回の最小変更に含めない。

## 10. 残る未解決事項

1. **stdoutの全障害を含む原子性。** 生成エラーまでなら維持できるが、書込/flush障害後の0バイト保証は可搬なstdoutでは成立しない。ファイル宛保存の原子的置換は別契約である。絶対要件のままなら実装完了を宣言しない。
2. **処理系全体のメモリ保証。** 出力と生成領域のペイロードは制限できても、無制限のソース長・AST幅・宣言数・診断文字列と通常のBox確保が残る。全RSS上限・全確保失敗のError化には別の予算設計が必要。既存の長い有効ソースへの互換性も検討する。
3. **計数後再走査の実時間。** 単純な参照列では十分と予測するが、長い式・多い条件・文字列検査の二重実行は未測定。RSS・時間の採用判定を実測で行う。値の再生成による高速化はしない。
4. **ABC251-F/383-Eの大規模疎グラフ。** 小さい上限変更は全候補列挙を解決しない。最大木やパス＋1辺は、一般のM・辺集合の代替ではない。
5. **ABC420-Eの構成範囲。** 最大Qの種別2列は資源対応できても、現行の子番号がクエリ番号に結び付く構成を一般の大規模な辺追加列へ拡張するには別設計がいる。
6. **ABC298-Cの解答予算と多様性。** 全挿入または1枚への問合せで最大Qを通せても、多様な状態遷移・多重度・箱集合・問合せ混在を扱えたことにはならない。
7. **省容量構成の互換性。** 補助の幅1生成を省くと後続PRNGがずれる。新ソースの到達構造と乱数順序を明示し、従来正常ソースの1,010バイト一致基準を緩めない。
8. **実装対象外の機能不足。** 異長文字列、可変区画U1、Unicode/標準漢数字/式構成などは残る。unsupportedのXMASCON18-Jは資源上限改定で改善しない。

最初の出力方式変更は39生成器全体の出力保存を軽くするが、上限未達件数そのものは変えない。続くT/B/G改定でABC383-E・ABC420-Cの既知6条件と、新設するABC355-Dの最大条件を改善できる。ABC420-Eは固定列の省容量構成または配列改定も必要である。保存改定を併用するとABC216-D、ABC251-FのN633、ABC298-Cの全挿入、ABC401-Fの両最大を現在の構成のまま収容できる見込みであり、大規模疎グラフと多様な解答予算付きクエリ列は生成アルゴリズムの課題として残す。
