### 1.2 現行DSLで表せるもの

| 項目 | 現行の契約と評価上の注意 |
| --- | --- |
| 基本型 | 符号付き64bit整数、整数一次元配列、ASCII固定長文字列、共通幅の文字列配列。長さは宣言時の生成済み値で決められ、実行ごとに変えられる。 |
| 宣言・保存 | 宣言とU1は `generate` 直下のみ。ループ・分岐内に宣言できない。セルは一度だけ初期化し、上書きできない。容量は未使用・未初期化の枠も数える。 |
| 依存関係 | 先に生成済みのスカラー・セルを長さ・添字・範囲・条件に利用可能。ソース順に実行し、依存関係を自動解決しない。整数の定値・コピー・計算結果は幅1の範囲でも保存できるが、乱数を消費する。 |
| 計算・条件 | `+ - * / %`、単項符号、括弧、間接添字、整数の6比較。文字は等値・不等値のみ。論理演算はなく入れ子のifで表す。中間値もi64であり、オーバーフローを避ける必要がある。 |
| 反復・行 | ネストしたfor、if/else、1行のトークンを組み立てるrow。空の反復で0行・0要素も表せる。整数配列長0は不可だが、容量1以上の保存領域の一部だけを使う回避は可能。 |
| 一意性 | `A in unique(range) except(...)` は全セル未初期化の整数配列全体が対象。除外は整数式または初期化済み整数配列全体。区間対象、区間除外、ループ内U1、文字のU1はない。 |
| 文字列 | 非空白のASCII `0x21..0x7E` の候補抽選と、文字リテラル・文字セルのコピー。単一文字列の長さは生成値で指定可能。文字列配列の行ごとの異長、部分文字列を連結した1トークンの出力、Unicodeは直接扱えない。 |
| 出力 | 生成完了後の値を参照する。整数・文字・文字列・配列を行に配置し、1スペース区切り・LFで出力。数式、ループ変数、リテラルは直接出力できず保存値が必要。文字セルをrowに並べても間にスペースが入り、文字列連結にはならない。 |
| 構造制約 | 木・グラフ・状態付きクエリ・総和の専用型はない。ただし親構成、平坦配列、累積配列と分岐で保証できる場合がある。専用構文がないことだけを不対応の根拠にしない。 |

### 1.3 実行量・容量の上限

以下の「1ケース」はAtCoderの内部テストケース1個ではなく、**1回のDSL実行が出力する入力ファイル全体**。T個のケースがあっても上限はリセットされない。

| 対象 | 上限 |
| --- | ---: |
| 整数配列の1配列・全配列の宣言セル数 | 各1,000,000 |
| 生成整数数（スカラー、補助値、幅1の初期化を含む） | 1,000,000 |
| 文字セル数（整数とは別枠、全宣言の合計） | 1,000,000 |
| U1の除外前の候補幅W | 1,000,000 |
| U1の正規化前の除外読取数e | 1,000,000 / 操作 |
| U1作業列のペイロード | `8*(W+e)≤16,000,000` バイト |
| 出力トークン数 | 1,000,000 |
| 出力サイズ（区切り・LF込み） | 8,388,608バイト（8 MiB） |
| forへの進入1回の反復数 | 1,000,000 |
| 累積実行量 | generate/inputそれぞれ10,000,000単位（適用条件は後述） |
| 制御 / 式の深さ | 32 / 128 |

累積実行量は、ネストfor・row・ifを含むブロック、およびU1を含むgenerateに適用される。文1単位に加え、forへ進入するごとに反復数を課金する。U1にはさらに `k+W+e*ceil(log2(e+1))` を課金する。平坦な旧構文だけのブロックには累積実行量の上限が適用されないが、他の上限は残る。U1のペイロードはプロセス全体のメモリ上限ではない。

SplitMix64とu64 seedを使用し、同じバージョン・同じソース・同じseedの成功出力はバイト単位で再現される。幅1の整数抽選も乱数を消費する。文字の固定コピー、条件、出力は消費しない。有限のseed観測を一様性や全入力への到達の証明に使わない。

## 2. 選定方針と分類の基準

### 2.1 問題を先に固定する

6分野各5問とし、単純な対照問題、依存関係、集合、異長の列、状態付き入力、構造保証、総量制約、巨大な数値トークンを組み合わせた。古いABC095・117・150等と、新しいABC401・413・420・423・425等を混在させる。解法の実装難易度と入力生成の難易度は分けて扱う。

**ABCのB〜Fを29問**、文字種・式形式の対照として**Xmas Contest 2018のJを例外的に1問**選んだ。英字・数字の問題だけでは測れない非ASCII入力を含めるためである。ARC追加はない。この1問の例外と、分野による層化抽出である点をレビュー対象とする。AtCoder全体を無作為抽出した標本でも、難易度分布の推定でもない。

第3節のID・URL・分野・バッチは本フェーズの確定リストとする。第4節はそのリストへのDSL評価であり、制約や容量の問題が見つかっても母集団を変えない。将来分類が変わる場合は、元の予測と変更理由を残す。既存10問はいずれも重複選定していない。

### 2.2 statusとcoverageを別に記録する

| status | 暫定判断 |
| --- | --- |
| supported | 現行構文で、出力した入力が公式の全入力制約を満たす構成と根拠を説明できる見込み。規模・形・値の選び方を限定してよい。 |
| format-only | 行・トークンの型と並びは作れるが、採用する生成方針で意味的制約を保証できる根拠がまだない。単に専用構文がないという理由では付けない。 |
| unsupported | 入力形式・必須の文字種など自体が現行DSLで再現できない。 |

coverageは、主要構造と公式の規模・値域を幅広く扱える見込みなら `representative`、規模・形・独立性・文字列長等を限定するなら `restricted`、有効な生成方針がない場合は `none`。`format-only`・`unsupported` は `none` とする。**supportedは全有効入力への到達も、一様性も意味しない。** 固定値・小さい素数表のような弱い構成も公式制約を保証できるならrestrictedとして可視化する。

そのため、異長文字列の問題を一律unsupported、素数や総和を含む問題を一律format-onlyとはしない。例えば共通幅の文字列だけに限定すれば有効な入力を生成できる。問題単位のstatusに加え、**一般形・公式境界の未対応を別に記録**する。これにより「supportedが多いので一般的なコーパスを作れる」と誤認しない。

## 4. 各問題の入力制約と対応見込み

記法: `;` は改行、`[X_i]×n` はn行、`row(...)` は1行内の列を表す。これは入力形式の要約であり、実行可能なDSLではない。公式の数値入力は、P03/P04/P11/P12/P13/P14/P15/P25/P28/P29の文字列・文字トークンを除き整数として扱う。各項目の「不足・制限」は、公式制約そのものと混同しない。

### 4.1 整数・配列・数値間の依存制約

**P01 — ABC095-C / arc096_a — supported / representative**

- 公式: [Half and Half](https://atcoder.jp/contests/abc095/tasks/arc096_a)。入力は `A B C X Y` の1行。
- 制約: `1≤A,B,C≤5000`、`1≤X,Y≤100000`。他の大小関係・相異性・総和制約はない。
- 方針・根拠: 5スカラーの独立した範囲抽選で全入力制約を保証できる。`2C<A+B` 等は解法・答えの分岐であり、入力制約には追加しない。
- 容量・構造: 生成・出力とも5整数、最大29バイト。DSL機能の不足・構造制限は見込まない。購入量の境界だけでなく価格の等号・逆転を固定プロファイルで確認する。
- 登録上の課題: 現行verify_corpus.pyのURL組立規則は `abc095_c` を要求する。公式slugと一致しないので、後続フェーズでは公式task IDを保持する登録方法・URL検証の調整が必要。DSLの不対応とは数えず、今回スクリプトは変更しない。

**P02 — ABC117-D / abc117_d — supported / representative**

- 公式: [XXOR](https://atcoder.jp/contests/abc117/tasks/abc117_d)。入力は `N K; A_1 ... A_N`。
- 制約: `1≤N≤100000`、`0≤K,A_i≤10^12`。Aの一意性は要求されない。最大化に使う `X≤K` は入力変数間の制約ではない。
- 方針・根拠: N、K、長さNのAを独立生成。重複、0、ビット境界を許す。
- 容量・構造: N+2生成整数・出力トークン、出力上界 `14N+21` バイトで十分。配列・i64・出力上限内。XORのDSL演算を追加する必要はなく、主要な入力構造の制限は見込まない。

**P03 — ABC192-D / abc192_d — supported / representative**

- 公式: [Base n](https://atcoder.jp/contests/abc192/tasks/abc192_d)。入力は `X; M`。
- 制約: Xは数字列、`1≤|X|≤60`、先頭は0でない。`1≤M≤10^18`。Xをある基数で解釈した値がM以下になるという入力保証はない。
- 方針・根拠: 非出力の長さを先に生成してstringを宣言し、先頭を1〜9、残りを0〜9の候補で初期化。X自体をi64に変換しない。
- 容量・構造: 60文字以下、出力2トークン・81バイト以下。長さ1、全9、M最小・最大を含められる。基数計算や巨大整数演算は入力生成に不要。

**P04 — ABC301-D / abc301_d — supported / representative**

- 公式: [Bitmask](https://atcoder.jp/contests/abc301/tasks/abc301_d)。入力は `S; N`。
- 制約: `1≤|S|≤60`、文字は `0,1,?`、`1≤N≤10^18`。
- 方針・根拠: 長さとNを生成し、Sの各文字を3候補から抽選する。N以下の置換結果が存在しない入力も有効なので除外しない。
- 容量・構造: 60文字・2出力トークン・81バイト以下。全?、先頭0、?なし等の境界も作れる。文字列から整数への変換・ビット演算は必須ではない。

**P05 — ABC423-C / abc423_c — supported / representative**

- 公式: [Lock All Doors](https://atcoder.jp/contests/abc423/tasks/abc423_c)。入力は `N R; L_1 ... L_N`。
- 制約: `2≤N≤200000`、`0≤R≤N`、各Lは0または1。
- 方針・根拠: Nを先に、RをNに依存する範囲から生成し、Lを二値で初期化する。移動・開閉の解シミュレーションは入力の有効性には不要。

- 容量・構造: 各問い合わせの出力量は過去の挿入数以下なので、総出力量を保守的にQ²≤65536と抑えられる。これはatcgenが出す入力のサイズとは別の制約。入力は3Q+2≤770トークン・約0.004 MB以下。箱と値の重複、種別の混在は扱うが長い操作列を除外する。
- 不足: 大規模での箱の多重度・値ごとの相異なる箱数と総出力予算の効率的な管理。過去に存在する値の参照だけでは総出力量の保証にならない。単純な累積予算による保守的な上限管理は現行でも可能で、正確な状態管理とは分ける。

**P24 — ABC253-F / abc253_f — supported / representative**

- 公式: [Operations on a Matrix](https://atcoder.jp/contests/abc253/tasks/abc253_f)。入力は `N M Q; query×Q`。形式は `1 l r x` / `2 i x` / `3 i j`。
- 制約: `1≤N,M,Q≤200000`。種別1は `1≤l≤r≤M,1≤x≤10^9`、種別2は `1≤i≤N,1≤x≤10^9`、種別3は `1≤i≤N,1≤j≤M`。種別3が1回以上必要。
- 方針・根拠: 必ず種別3とする位置を1つ抽選し、それ以外の種別を抽選。範囲端点はlの後でrを生成する。値は共用の4配列（種別と最大3引数）で保存し、ifで必要な幅を出力する。
- 容量・構造: 最大約4Qセル・4Q+3≤800003トークン、入力は約5.8 MB以下。N×Mの実際の行列は入力に存在しないので、その巨大な配列を確保する必要はない。アンカー方式で種別3の存在を保証できる。

**P25 — ABC420-C / abc420_c — supported / restricted**

- 公式: [Sum of Min Query](https://atcoder.jp/contests/abc420/tasks/abc420_c)。入力は `N Q; A_1 ... A_N; B_1 ... B_N; [c_i X_i V_i]×Q`。
- 制約: `1≤N,Q≤200000`、`1≤A_i,B_i,V_i≤10^9`、cは文字A/B、`1≤X_i≤N`。
- 方針・根拠: 整数配列と1文字列配列を生成し、クエリのc・添字・値を出す。通常はN,Q≤100000。更新後のA/BをDSL側で計算する必要はない。
- 容量・構造: 出力は `2+2N+3Q` トークン。**N=Q=200000は1,000,002トークンで上限超過。** 全値10^9・全添字200000なら出力は8,400,014バイトで8 MiBも超える。いずれも有効な公式入力で、記述短縮では解消できない。
- 不足: 出力上限の扱い。N,Q≤100000なら500002トークン・約4.21 MB以下で、整数保存も約400000セル、文字は100000セル以内。通常プロファイルの規模制限以外に配列更新の意味制約はない。

### 4.6 複数テストケース・総和制約・複合形式

**P26 — ABC216-D / abc216_d — supported / restricted**

- 公式: [Pair of Balls](https://atcoder.jp/contests/abc216/tasks/abc216_d)。入力は `N M; [k_i; a_{i,1} ... a_{i,k_i}]×M`。
- 制約: `1≤N≤200000`、`2≤M≤200000`、各k_i≥1、`Σk_i=2N`、色は1〜N、各色が全筒を通してちょうど2回。従ってM≤2Nも必要。筒を空にできる保証はない。
- 方針・根拠: 通常N≤4096、`2≤M≤min(2N,256)`。1〜2NのU1順列から色番号を剰余で1〜Nへ対応させ、色の参照用配列を介して出力する。各色に対応する元番号が2個あるので回数は正確に2。長さは残量から将来の筒に1個ずつ予約して配り、最終筒へ残量を置く。
- 容量・構造: 通常の出力は `2+M+2N≤8450` トークン、0.05 MB未満。全筒で独立なU1を行う方法では色の総出現数を保証できない。通常範囲内では任意の色配置と正の長さ配分を構成対象にできるが、規模は限定する。
- 不足: 最大規模に向けた省メモリ化。順列2N・色の参照N・長さM・累積位置M+1の保存方式は `3N+2M+1` セルで、N=M=200000では容量を超える。公式出力自体は600002トークン・約4.21 MB以下。多重集合シャッフル・回数制約の専用構文は便利だが、少なくともこの制約は既存U1と写像で保証できる。

**P27 — ABC284-D / abc284_d — supported / restricted**

- 公式: [Happy New Year 2023](https://atcoder.jp/contests/abc284/tasks/abc284_d)。入力は `T; [N]×T`。
- 制約: `1≤T≤10`、`1≤N≤9*10^18`、相異なる素数p,qで `N=p²q` と表せる。単に1〜9*10^18から抽選するだけでは公式制約を保証できない。
- 方針・根拠: 例えば素数表 `{2,3,5,7}` を明示的な分岐で選び、異なる2つの添字を使ってp,qを選ぶ。p²qを幅1の初期化でNへ保存する。既知の素数を使うこととp≠qの保証で有効になる。
- 容量・構造: この表ではN≤245、T≤10なので小容量・出力11トークン以下。公式Nの上限9*10^18はi64最大値未満だが、任意のp,qの積の中間値まで安全とは限らない。
- 不足: 表に依存しない大きい素数の選択、上限から逆算した積の安全な範囲。小さい表だけでは大素因数・値域上端を覆えない。素数判定がないことを形式不対応とはしないが、代表的な入力分布には達しない。

**P28 — ABC339-F / abc339_f — supported / restricted**

- 公式: [Product Equality](https://atcoder.jp/contests/abc339/tasks/abc339_f)。入力は `N; [A_i]×N`。
- 制約: `1≤N≤1000`、`1≤A_i<10^1000`。上限は厳密な不等号。`A_i*A_j=A_k` は数える対象の条件であり入力保証ではない。
- 方針・根拠: Aを整数型ではなく数字文字列として出力。通常は共通桁数Dを1〜1000から選び、長さDのN行を生成する。先頭を1〜9、残りを0〜9にすれば1以上10^1000未満を保証できる。
- 容量・構造: N*D≤1,000,000文字、出力N+1≤1001トークン・最大1,001,005バイト。i64の値域不足だけを理由にunsupportedとはしない。N個の桁数が共通のため、1・巨大値・その積など桁数の異なる数を混ぜる主要構造は欠ける。
- 不足: 異長文字列を保持・出力する一般的な方法。N上限1000なので個別の文字列宣言を1000個展開する回避は原理上可能だが、現段階の通常方針には含めない。展開版を採用する場合は記述量と容量の根拠を実測して分類を再検討する。巨大整数の乗算機能は入力生成自体には必須でない。

**P29 — ABC353-E / abc353_e — supported / restricted**

- 公式: [Yet Another Sigma Problem](https://atcoder.jp/contests/abc353/tasks/abc353_e)。入力は `N; S_1 ... S_N`（文字列は同じ行）。
- 制約: `2≤N≤300000`、各S_iは非空の英小文字列、`Σ|S_i|≤300000`。文字列の相異性は要求されない。
- 方針・根拠: 共通長Lを `1..=floor(300000/N)` から選び、文字列配列を生成して全体を1行出力。これで総長N*Lを保証する。共通接頭辞の長さを先に選び、その範囲を文字コピーすれば接頭辞の濃淡も変えられる。
- 容量・構造: 最大300000文字、N+1≤300001トークン、出力 `N*L+N+digits(N)+1≤600007` バイト。最大Nでも同長1文字なら出力できる。一方、異なる長さの文字列、真の接頭辞関係、総長を1本へ集中する構造が欠ける。
- 不足: 異長文字列の集合、文字列区間の空白なし出力、生成済みの長さへの予算配分と保存領域。長さの総和だけは累積配列で管理可能。パディングした行からセルをrowで出しても空白が入り、1トークンの文字列にはならない。

**P30 — ABC413-E / abc413_e — supported / restricted**

- 公式: [Reverse 2^i](https://atcoder.jp/contests/abc413/tasks/abc413_e)。入力は `T; [N; P_0 ... P_(2^N−1)]×T`。
- 制約: `1≤T≤100000`、各 `1≤N≤18`、各Pは1〜2^Nの順列、ファイル全体で `Σ2^N≤300000`。
- 方針・根拠: 通常はT≤64。2の累乗表を累積の倍算で作り、各ケースの長さL=2^Nを残り総長と将来の最低2要素の予約から選ぶ。累積オフセットで平坦化する。Pの位置jには `((a*j+b)%L)+1` を保存し、aを正の奇数、bを0〜L−1から選ぶ。Lが2の累乗なのでgcd(a,L)=1となり、各ケース内の順列性を保証できる。
- 容量・構造: 総長300000とケース用補助配列により、T≤64なら整数容量に余裕がある。公式出力は最大 `1+T+Σ2^N≤400001` トークン、保守的にも約2.41 MB以内。ケース内の要素0始まりはDSLの1始まり添字へ対応を明示する。
- 不足: 多ケースの各区間を独立のU1で初期化する機能。現在のU1はループ内・部分配列に適用できない。採用するアフィン順列は全順列を覆わず、逆順を作れても一般のシャッフルではない。T=1の独立境界プロファイルなら全域U1で任意順列を扱えるが、多ケース全体のcoverage改善とは数えない。総和と累乗の計算は現行でも構成可能。

## 5. DSLの対応見込みの読み方

新規は `supported=29 / format-only=0 / unsupported=1`、coverageは `representative=16 / restricted=13 / none=1` の予測となった。format-onlyを0件としたのは、その枠を埋めるために既存の構成法を無視しなかったためである。例えばP27の小さい素数表、P28/P29の同長制限も、弱いが有効入力を保証する構成なのでsupported/restrictedに数える。実装後、保証の欠落が発覚した場合はformat-onlyへ修正する。

これは「29問で実用的な生成が完成する」という結果ではない。P09の包含関係だけの集合、P13の全x相異、P18の星の鎖、P27の小さい素数表、P28/P29の同長文字列、P30のアフィン順列などは主要構造を大きく制限する。これらの一般形や、P19/P25の公式最大入力は現行DSLで採用方針のまま扱えない。P11は有効なトークン自体を出力できない。

各問題について、次の3点を別々に判定する。

1. **形式**: 行数、各行のトークン数、文字列の連結、種別ごとの分岐を再現したか。
2. **有効性**: 値域、相異性、連結、次数、存在条件、ケース間総量など、公式の全制約を保証したか。
3. **広さ**: 規模・値域・構造・独立性・境界のどこが不足したか。小さい有効ケースが存在するだけでrepresentativeにはしない。

入力形式が作れることは公式制約を満たすことの証明ではない。逆に、解答で最大化・総和・文字数制約を解く問題でも、その条件が入力保証でなければ生成器へ課さない。P10/P14/P22/P24/P28をその誤認の対照に使う。

### 6.3 複数ケース間の資源管理

P27はT個の数値で、追加のケース間総和制約はない。P30はΣ2^Nをファイル全体で管理する。P20は2つの木を連続出力するが公式の合計頂点数制約はなく、DSL側の容量を共有する。P09/P26/P29は明示的なTがなくても総要素数・総長を共有する。全てを「複数ケース未対応」という1項目にまとめない。

予算値は生成済みの累積配列へ一度ずつ保存できる。残りqケースに最低mずつ必要なら、現在の抽選後に少なくともq*mが残る範囲を使う。固定した正確な総和を狙う際には、将来の最大容量も予約した下限が必要。専用のsumやmaxだけを追加しても、この実現可能性の設計は不要にならない。

## 7. Phase 7-B以降の実装順序案

各フェーズの対象10問は第3節から動かさない。DSLはまず現行のまま評価し、機能追加の検討はその評価結果から独立した後続議題とする。

1. **各バッチ開始時に公式制約の確認記録とチェッカー設計を先に確定する。** 公式値域、型・行数、各構造保証、解の条件との境界、必要な負例を列挙する。生成器の限定値をチェッカーの上限に使わない。
2. **通常プロファイルの構成根拠と資源式をレビューする。** P09/P23/P27等の弱い構成でも制限を明示し、保証できなければformat-onlyとして残す。P11は未対応のまま登録できる設計を使い、代替のASCII問題へ変えない。
3. **保証を確認した問題だけをsupportedの生成器として実装する。** 不対応はメタデータ・チェック方針と失敗理由を残し、架空のgenerator.genは置かない。これは後続フェーズの作業であり、7-Aでは行わない。
4. **共通seed、固定境界、構造プロファイル、チェッカー負例を検証する。** 実測と構成上の根拠の両方が揃ってから分類を確定する。
5. **バッチ終了時に母集団10/20/30問全てを分母として報告する。** 実装不能・未実装・容量超過を成功件数から黙って除かない。旧10問の回帰結果は新規分と分ける。

バッチ1ではP01/P03/P06/P15/P16/P22で基本の制約・出力を確認し、P09/P18/P26/P28で集合・特殊木・総数・巨大トークンの制限を確認する。P01の公式URLと現行メタデータ検証の衝突はこの時点の登録課題として解決する。

バッチ2ではP02/P05/P08/P12/P21で数値、集合、文字の昇順、状態の帰納法を確認し、P13/P17/P23/P27/P30で広い抽選、一般グラフ、解答出力量、素数、ケース間総長を検証する。

バッチ3ではP04/P07/P10/P14/P24で不存在も合法な入力と存在アンカーを確認し、P11/P19/P20/P25/P29で文字型、出力上限、複数構造の容量、異長文字列の限界を確定する。難しい問題を後半だけへ集中させる順序ではない。

## 8. 評価指標と受け入れ条件

### 8.1 記録する単位と分母

問題単位のstatus/coverageと、生成条件単位の検証結果を分ける。「条件」は問題ID・生成器のソース識別子・プロファイル・seedの組。通常プロファイル、固定境界、制限外の挑戦プロファイルを別集計にする。まだ実装していない問題の成功率は0%とも100%ともせず `未測定` とし、母集団からは除かない。

| 指標 | 測定・報告方法 |
| --- | --- |
| status件数 | supported / format-only / unsupportedの全件数、分野別・バッチ別・全40問。7-Aの予測と実測後の分類の遷移も残す。 |
| coverage件数 | representative / restricted / noneの全件数。restrictedは規模・構造・値域・独立性・保存方式の各制限を重複可で集計する。 |

### 8.2 seedと任意seedの正当性

共通seedは既存の `0,1,42,100,7,19,23,49,127,255,1024,65535,2^63,2^64−1` を継承する。追加seedや走査範囲を使う場合は実行前に範囲を固定して記録する。最大ケースを全seedで繰り返さず、通常と境界の時間を分離する。timeoutの変更で失敗を隠さず、実行環境・バージョン・ソース識別子・seed・所要時間を保持する。

少数seedの成功は実装の回帰観測であり、任意seedに対する正当性の証明ではない。supported確定には、少なくとも以下の説明を問題ごとに要求する。

- **範囲の実現可能性**: 全反復で下限≤上限、配列長・添字が有効、将来分の最低必要量を残す。中間算術もi64内。
- **単一初期化と参照**: 全出力セルが正確に1回初期化され、分岐や空反復でも未初期化読み取りがない。使用しない領域の容量も算入。
- **意味的な不変条件**: 木の新頂点接続、順列の全域U1、出現回数の写像、状態サイズ非負、集合の一意性、ケース間残量等を帰納的に説明。
- **資源の上界**: 整数セル・生成整数・文字セル・U1幅と除外数・内部仕事量・出力トークン・バイト・両ブロックの仕事量を式で算出し、最大プロファイルで照合。小さい通常seedだけで上限内と推定しない。
- **主張の範囲**: 全seedで有効である根拠と、どの入力集合を対象にするかを分ける。偏りや有限seedによる到達性は保証しない。

7-Aの予測との差異は分類ではなく確認範囲にある。P09の空集合・公式規模・総和上限、P18の公式最大N、P26のN最大とM最大を別条件で確認できた。一方、P26の完全な最大組合せにはMaxMの補助セル等も含めた実装上の総容量衝突を確認した。7-Aにあった資源の概算は上書きせず、次節の実装の式を実測レポートと照合した。

### 10.4 任意seedでの制約充足と資源の根拠

実装は成功するseedだけを選別していない。通常設定に対する有効性は、以下の構成と範囲の不変条件に基づく。有限seedの通過だけから任意seedの正当性や分布の一様性を証明したとは扱わない。

- **P01/P03/P28**: 公式範囲のスカラーとASCII文字候補を使う。数字列は先頭1〜9・残り0〜9で、正・桁数上限・先頭条件を同時に保証する。P03/P28の数値トークンをi64へ変換しない。
- **P06**: 1〜NからN個を一意抽選する2回のU1は、それぞれ順列になる。配列間の除外は行わないのでP=Qも許す。固定Nにおける独立一様乱数語のモデルの説明と、入力全体の一様性は別である。
- **P09**: 共通Pは1〜Mの順列であり、先頭A_i要素の範囲と一意性を保証する。通常は `N*M≤16384`。空集合の固定条件でもrowは1空行を出し、総和は正に保つ。独立チェッカーに接頭辞・非空という制限は課さない。
- **P15**: アンカー位置だけ#に固定し、それ以外のセルだけ候補抽選するので、各セルは1回初期化、#は必ず存在する。1×1でも有効。
- **P16**: 内部の子i+1を既存の1〜iへ結ぶ帰納法で、連結性・非巡回性・辺の一意性を保証する。PとOrderは全単射、端点の昇順化は無向辺を保つ。任意の木は親を先に内部番号付けして構成対象にできるが、親構成は一様な木の分布ではない。
- **P18**: 各星の中心はOffset[t]+1、葉はその後のLevel[t]個。星tの2枚目の葉と次の星の1枚目の葉を接続する。中間の星の接続ポートが異なり、全レベル≥2なので存在し、各接続が異なる成分の未使用葉同士になる。内部辺と接続辺の保存添字は重複せず、合計N−1。P/Orderでこの性質を保つ。
- **P22**: 全クエリ位置でKindとXを生成し、Kind≠1の場合だけKを初期化・出力する。同じ条件で出力を分岐するため、不要なKの未初期化読取りはない。状態による追加の有効性条件はない。
- **P26**: 1〜2Nの全域U1を `((v−1)%N)+1` へ写像すると、各色の原像がちょうど2個なので全色2回になる。Color配列経由の参照で数式を直接出力せずに済む。各筒で残りの筒数分を最低1個ずつ予約し、最終筒に残量を置くため、空の抽選範囲・空筒・総長不足がない。

通常設定の資源上界は以下。Iは生成整数数、Aは宣言済み整数配列セル数、Cは文字セル数。補助値・未使用領域も計上する。G/Oは生成側/出力側の仕事量。単純な旧構文だけで実行量制限の適用がない部分も、同じ計数を参考上界として示す。全式の最大値と中間算術はi64内である。

### 10.5 ABC303-Eチェッカーの独立性

チェッカーは入力のNと辺だけを使う。最初に値域・辺数・自己ループ・重複/閉路・連結性を検証し、木であることを確かめる。その後の判定は次の必要十分条件に基づく。

1. 最終状態の葉は、接続に使われなかった元の星の葉である。従ってその隣接点は星の中心に強制される。任意の葉からこの中心を根にする。
2. 元の中心間の接続は必ず「中心―葉―葉―中心」の3辺なので、根から距離が3の倍数の頂点を中心候補とする。中心の次数は2以上でなければならない。
3. 各非中心は次数2以下で、中心候補にちょうど1つ隣接しなければならない。この条件で全頂点が重複なく星に分割される。中心の隣接葉は少なくとも2枚。
4. 残った辺は葉同士のマッチングになる。星の縮約は木なので、接続辺を順に加えると常に別成分を結ぶ。各葉は1回しか使われず、接続時には次数1である。従って公式の手続きでこの入力を再構成できる。

この判定はO(N)時間・O(N)領域で、生成器の星の個数・サイズ・鎖・置換を読み取らない。星の接続木が分岐する独立例とそのラベル/辺向き/辺順変更を受理する。逆に中心同士の直接接続、同じ葉の再利用、星に分割できないパス等を拒否する。

テストではN=3〜6の全ラベル付き木1440個について、全ての「接続辺の候補を切る」部分集合を列挙し、残る成分がレベル2以上の星、切った辺が元の葉の一回利用かを調べる別方式をオラクルとした。深さ判定と全1440例で一致した。これは有限例の検証であり、必要十分条件の説明を置き換えるものではない。
